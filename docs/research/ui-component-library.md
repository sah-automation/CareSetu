# Research: Component library & UI foundation under the page-weight budget

**Ticket:** #179 (map #178 "Top-level UI Blueprint") · **Date:** 2026-08-21
**Question:** Which component-library/design-system approach should the CareSetu frontend standardize on - shadcn/ui, another headless option (Radix primitives, Headless UI, React Aria Components), or hand-rolled Tailwind components - given Next.js App Router + Tailwind, the NFR-003 1.5 MB page budget, bilingual EN/Hindi UI, accessibility needs, and a small team?

## Recommendation

**Standardize on shadcn/ui on the Tailwind v3 registry with the Radix primitive base**, adopting components lazily per feature need. Use **React Aria Components selectively** for locale-sensitive input widgets (date pickers, internationalized number fields) where its Intl layer earns its bytes. Keep hand-rolled Tailwind for leaf presentational components only - which is exactly what the Phase 2.5 shell already does.

## Constraints recap

- **NFR-003:** initial page load ≤ 5 s on 4G; page weight ≤ 1.5 MB. Client-JS weight is a first-order concern (Tier-3/4 India users on 4G smartphones).
- **NFR-001:** no paid proprietary frameworks at launch - all candidates are free/open-source, so this constrains none of them directly.
- **Bilingual EN/Hindi UI** (`REQ-006`): both LTR; needs a string layer and locale-aware date/number inputs, not RTL mirroring.
- **Accessibility:** healthcare app; screen-reader and keyboard correctness is not optional.
- **Small team:** every dependency's maintenance surface counts against us.
- **Pinned stack** (`apps/frontend/package.json`): Next ^16.3 App Router, React ^19, **Tailwind ^3.4 (not v4)**, TypeScript 5.7, vitest/jsdom.

## Why this recommendation

1. **Bundle-to-a11y ratio fits the budget.** shadcn/ui ships zero library runtime - only copied source plus the Radix primitives each component sits on (Dialog: 12.6 KB gzip measured). Against a 1.5 MB total page budget that leaves room for content, fonts, and media, while keyboard/focus/screen-reader behavior comes from battle-tested primitives rather than our own code.
2. **Tailwind v3 pin is safe today.** shadcn explicitly keeps generating v3-style components for existing v3 apps and maintains legacy docs; we are not forced onto v4 to adopt it.
3. **React Aria where i18n actually bites.** Hindi-language date-of-birth and appointment inputs need Intl-aware parsing/formatting; React Aria is the only candidate with primary-source evidence of cross-screen-reader testing and built-in locale support. Adopting it wholesale would cost ~271 KB gzip of raw library weight and the steepest learning curve; adopting it per-widget via shadcn's `--base aria` option (or direct npm import) buys the i18n without the tax.
4. **Rejected alternatives.**
   - _Hand-rolled as default:_ smallest bytes, but a small team owning dismissable-layer focus management and combobox semantics in a healthcare app is an audit failure waiting to happen. Continue hand-rolling leaf presentational components only.
   - _Headless UI:_ component surface (~15, no Tooltip/Slider/Toast/DatePicker) forces a second pattern within months; release cadence is fix-only; weakest documented a11y story.
   - _Radix direct:_ viable but strictly more work than shadcn over the same primitives - shadcn supplies the styling/pattern layer we would otherwise write.
   - _Base UI (shadcn's new default):_ promising and actively developed (v1.7.0, Aug 2026), but too young; revisit once it accumulates production mileage. Pin the Radix base at init time.
5. **NFR-001 clean:** MIT-licensed, no paid tiers anywhere in the chain.

## Migration notes relative to the Phase 2.5 shell

The existing shell needs **no rewrite** - adoption is additive, component by component:

- **`src/components/dashboard/Sidebar.tsx`** (`Sidebar({ role, collapsed, onToggle }: SidebarProps)`): keep as-is. It is plain Tailwind markup with no interactive primitives beyond buttons. When mobile navigation needs a drawer, adopt shadcn `sheet`; when nav items need tooltips in collapsed mode, adopt `tooltip`. Do not adopt shadcn's wholesale `sidebar` block - it carries its own CSS-variable layout system tuned for v4 tokens.
- **`src/components/dashboard/Topbar.tsx`** (`Topbar()`): keep. When the role switcher or notifications area grows a menu, adopt `dropdown-menu` / `popover` there first - that is the natural pilot for the first shadcn additions.
- **`src/components/dashboard/types.ts`**: `Role`, `ROLE_LABELS`, and the width constants (`SIDEBAR_WIDTH_EXPANDED = "w-60"`, `SIDEBAR_WIDTH_COLLAPSED = "w-16"`, plus the `pl-*` margins) remain the single layout contract; any new shadcn-based navigation pieces must consume these constants rather than re-declaring widths.
- **`src/components/auth/icons.tsx`** (`IconProps` + 15 inline SVG icons): keep. Zero-dependency tree-shaken icons beat adding `lucide-react` (shadcn's default icon dep) just to match; if lucide is ever adopted, alias rather than duplicate.
- **`src/components/auth/otp/PatientAuthWizard.tsx`** (`PatientAuthWizard()` with internal `PhoneStep` / `OtpStep` / `DoneStep`, `StepDots`, `CountdownRing`): already hand-rolled and tested - do not rewrite. Adopt opportunistically when touched: `input-otp` pattern for OTP entry, `input`/`button`/`form` in `PhoneStep`, `alert-dialog` for resend confirmation. The CSS Modules files (`otpShared.module.css`, `variantB.module.css`) coexist fine; converge on Tailwind utilities + shadcn tokens long-term, no big-bang port.

## Adoption steps & guardrails

1. Run `npx shadcn@latest init` against the Tailwind v3 path; verify `components.json` records the v3 style explicitly (guards against the stale-style CLI drift in discussion #6714). Pin the Radix base at init.
2. Add components lazily per feature ticket - never bulk-add; each addition is reviewed like any other source file since we own it.
3. Keep the EN/Hindi string layer app-owned (shadcn adds no translations); use React Aria-based internationalized inputs for DOB/appointment fields.
4. Add a CI bundle-size check against the NFR-003 1.5 MB page budget (e.g., `@next/bundle-analyzer` + a hard budget assertion) so every adopted component's cost is visible at PR time.
5. Revisit the Base UI default decision (and the Tailwind v4 migration) as separate future tickets, not bundled into adoption.
