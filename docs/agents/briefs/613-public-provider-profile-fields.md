# Brief - 613 Extend the public provider profile with the new declared fields

**Ticket:** #613 · **Parent:** #599 · **Refreshed:** 2026-09-30
**Reading surface:** ~10.3K tokens (budget 10K) - marginally OVER; drop read-list item 1 to land at ~9.7K

## Scope

A doctor can fill their profile completely today and no patient sees any of it. The public provider profile response stops being a minimal verified-safe projection and carries the declared fields too - clinic name, specialties, languages, consulting days and hours, about text, years of experience, and the structured address parts. Visibility still gates on exactly the same condition as search, so if the tick is gone the profile is gone.

AC:

- [ ] The public provider profile response carries clinic name, a multi-valued specialty selection, languages, consulting days, consulting hours, about text, years of experience and the structured address parts.
- [ ] The visibility gate is unchanged - activation state plus the directory entry plus unexpired unrevoked credentials - and still agrees with search exactly.
- [ ] No artifact reference, contact detail or PHI is exposed by the widened response.
- [ ] The verified indicator is still derived, never stored and never widened to cover any declared field.
- [ ] The provider profile integration suite is extended to assert the new fields for an active doctor and no leak for an inactive one.

## Handoff notes

**Blockers, and what they will have landed by the time you start:**

- **#606** (structured profile columns and multi-valued specialty storage) - creates every field this ticket exposes: the clinic name, the multi-valued specialty column, the structured address parts, the multi-valued consulting days, the consulting hours, and the closed-vocabulary replacement for the free-text `languages` column. It also retains the existing display-address column as a **denormalised projection** of the structured parts, written by registration as the pre-structured value until the structured parts exist. That retention matters here: it means the old single-string address field is still being written, and you must decide whether the public response carries the structured parts only or the denormalised string alongside them. Prefer the structured parts, and treat the denormalised string as a registration-era compatibility value rather than something to widen further.
- **#602** (own the closed vocabularies) - gives the specialty, language and consulting-day lists a single owning home, so the mapper validates against that home rather than against the two places the specialty list currently lives (the `Specialty` string enum in the partner credential domain module, and the doctors-only check constraint on the directory index, which #606 drops).
- **#608** (practice section write) - is what makes clinic name, specialties and years of experience real, writable, doctor-owned values. It also extends the private read view, so the private console read and the public profile read will be reading the same columns through two different projections. That is intentional: they are different audiences with different field sets, not two sources of truth.
- **#609** (address section write) - writes the structured address parts and derives the practice position from the declared PIN.
- **#610** (about and notification section writes) - writes the about text.
- Transitive: **#607** (shared directory-entry refresh operation) keeps the directory entry's specialties and locality in step with the profile, so the widened response reflects a doctor's most recent save. It provably cannot touch the listed flag or any part of the verified derivation - which is the same trust property AC 4 depends on.

**The visibility gate must stay unchanged - by symbol name:**

- The gate is the `provider_visible` function in the credential-validity module, and it is the **same function** the search path calls. `get_provider_profile` applies it as a `where` condition on the directory-index partner id alongside the partner-id equality; the search path applies it as the first condition of its condition list. **Do not inline, duplicate, extend, or re-derive it.** AC 2's "still agrees with search exactly" is satisfied structurally, by continuing to call this one function - not by adding a test that compares two independently written predicates.
- The gate's four conditions, in the function's own terms: the directory entry's active flag is true; the profile status is `Active`; there is at least one approved-round credential; and no approved-round credential is invalid (expired or revoked). A partner failing any one of them raises `ProviderProfileNotFoundError`, mapped to a 404 - never a 200 with a hidden flag. The 404 is also the privacy posture: a hidden partner must read exactly like a missing one.
- **AC 4's rule about the verified indicator.** `verified` stays a derived field, never a stored one, and it is currently hardcoded to `True` in the mapper because reaching the profile already implies all four gate conditions hold. Widening the payload does **not** widen `verified`: it means what it means today and nothing more. Do not add a `verified`-adjacent flag, do not make `verified` conditional on any declared field, and do not introduce a second indicator for the declared band. A patient must be able to tell "the platform checked this" from "the doctor said this" by which field they are looking at, not by a flag's value.
- **Where the mapper's `verified=True` and `status="verified"` shortcuts live.** Both are inside the `ProviderProfileView` construction at the end of `get_provider_profile`: the top-level indicator is set to true unconditionally, and each credential's status label is set to `verified` unconditionally, because the gate already guarantees every credential on a reachable profile is valid. Those shortcuts are load-bearing for the frontend's trust rendering; leave them exactly as they are.

**Judgement calls made while mapping this surface:**

- **The route unit suite's leak test will need a deliberate edit, not a deletion.** It scans the whole raw response text for a forbidden-substring list that currently includes `practice_address`. You are replacing that field with the structured address parts, so `practice_address` legitimately stops being forbidden while the new address field names become allowed. Read the test as a substring scan over the entire serialized body, not a key-by-key assertion: any new field whose name happens to contain a forbidden substring will trip it, and a field named e.g. anything with `phone` or `artifact` in it will fail for a reason that has nothing to do with disclosure. Update the list deliberately, keep the whole-response scan property (it is a stronger assertion than a key allowlist), and add the new field names to the positive assertions in the same suite.
- **The frontend does not need to change, and that is not an oversight.** The public directory profile client's `ProviderProfile` interface and its `isProviderProfile` shape guard check only the presence and type of the fields they already know; a widened backend response passes both unchanged, so `tsc --noEmit` stays green and the client silently ignores the new fields. That is correct for this ticket - the declared band's rendering is owned by #618 (extract the shared public-profile renderer) and #619 (render the declared band on it). Leave the client type alone; widening it before the renderer exists would freeze a contract with no consumer. Record the widened response shape in the backend model docstrings instead, so the frontend ticket has something authoritative to read.
- **Only the provider profile widens, not the search response.** `DirectoryEntry` and the directory search response stay as they are; #612 owns the search read path and the question of whether its specialty projection widens. Do not widen both in one change - the visibility gate is shared, and two simultaneous widenings make a leak or drift report ambiguous.
- **No migration, no event, no module link.** This is a response-widening inside the owning module. Do not register a new event name (the analytics events for this surface already exist and are unchanged), do not add a cross-module call, and do not add a foreign key.
- Relevant ADRs: **ADR-0011** (credential expiry, lazy-on-read plus daily sweep) is the standing justification for deriving visibility on every read and for the "tick gone = card gone" invariant that AC 2 and AC 4 protect - widening the payload must not weaken it. **ADR-0012** (directory entry unit per partner) is why the profile resolves through exactly one directory-entry row and why that row is the join anchor. **ADR-0003** (db-per-module isolation) is why the service-area vocabulary table carries no foreign key from the profile, which is what lets the area projection change without a schema change. **ADR-0020** (private profile-media bucket) is the standing reason no artifact ref or media path appears in this response: photo bytes live in a private prefix and only a ref lives in SQL, and a ref is exactly the kind of thing AC 3 forbids widening into. **ADR-0006** (iam facade split) is not in scope.
