# Brief - 609 Add the address section write that derives the practice position

**Ticket:** #609 · **Parent:** #599 · **Refreshed:** 2026-09-30
**Reading surface:** ~9.7K tokens (budget 10K) - within budget
**Set position:** second of the three section-write briefs in this batch (#608, #609, #610), and the largest of the three. Read-list items 1-5, 9, 11, 12 and 13 are the same anchors as in #608 and #610, described the same way, so a reader moving between the siblings sees one set of seams.

## Scope

The heart of the defect fix. A doctor enters a building and street, an optional landmark, a locality, a city and a 6-digit PIN code - never a coordinate - and the backend resolves the PIN against the bundled centroid dataset and writes the derived practice position from it, then re-derives the directory entry. A doctor who corrects a wrong sign-up PIN can now actually correct it. A PIN that cannot be resolved fails this section alone, with a field-level error the client renders under the PIN input, and leaves every other edit untouched.

### Acceptance criteria

- [ ] The address section write accepts the structured address parts and no latitude or longitude, resolves the PIN, writes the derived position onto the profile, rewrites the display address projection, and calls the shared directory refresh.
- [ ] An unresolvable PIN rejects this write with a 422 whose detail is keyed to the PIN field, and writes nothing.
- [ ] A PIN resolving outside the peri-urban belt still saves, and the response carries the warning that tells the doctor their listing will surface as an outside-your-area result.
- [ ] A subsequent directory search returns the doctor at the new position.
- [ ] The write is scoped per doctor for idempotency keys and rechecks that the doctor is active under a row lock.
- [ ] A doctor whose PIN is unlisted still cannot save their address - the data gap is a follow-up, not silently worked around - and the field-level error is what the doctor is shown.
