# Brief - T01 Phase 5 schema foundation (partner + iam operator MFA)

**Ticket:** #244 · **Parent:** #243 · **Refreshed:** 2026-08-31
**Reading surface:** ~8.5K tokens (budget 10K) - within budget

## Scope

The database foundation Phase 5 depends on: the expanded `partner` schema (a scaffold today holding only `partner_identities` with a single `id` column) and the `iam` schema additions for operator MFA. Purely schema + model work - no business behaviour.

Specifically:

- `partner` schema: `partner_profiles` (partner type: doctor | lab | chemist, lifecycle status: Registered / Under Verification / Active / Rejected, practice location/geo mandatory, optional service area defaulting to Daltonganj), `partner_credentials` (credential type per partner type, verified flag, expiry, artifact refs to encrypted object storage), `partner_verifications` (operator queue row, round/version, status, decision, required reason on reject, per-round `verification_started` trail), `service_areas`. The `partner_outbox` table name already exists as a contract and must be created to match it (keeps the T6a boundary check green).
- `iam` schema: fields for operator MFA enrollment/verification.
- SQLAlchemy models matching these tables (product `partner` schema, `iam` schema), following the existing `Table(name, MODULE_METADATA, schema=...)` pattern.
- Two alembic migrations: `v4.0__init_partner.sql` and `v4.1__iam_roles_mfa.sql` per the repo `vN.N__slug` convention.

Acceptance criteria (from #244 body):

- [ ] Alembic migrations apply cleanly on a fresh database (`migration-check` single-head gate passes; no cross-schema FK leaks)
- [ ] `partner` schema exposes `partner_profiles`, `partner_credentials`, `partner_verifications`, `service_areas`, and `partner_outbox`
- [ ] `iam` schema carries the operator MFA columns
- [ ] SQLAlchemy models exist for every new table and match the migrations (integration schema test passes)
- [ ] Existing T6a module-boundary check still passes (outbox table name contract holds)

**Caution flags for the implementer:**

- `tests/integration/test_iam_schema.py` asserts the iam schema holds exactly five tables (`IAM_TABLES` exact set). If the operator-MFA fields require a NEW iam table (rather than columns on `iam_identities`), that exact-set assertion and `test_bootstrap_schemas.py`'s `EXPECTED_*` sets must be updated in the same change. Decide MFA-as-columns vs MFA-as-new-table from the spec and reconcile these tests.
- `tests/integration/test_bootstrap_schemas.py` also asserts the union of expected tables is exactly `EXPECTED_IAM_TABLES | ... | EXPECTED_AUDIT_TABLES`. Adding partner tables requires extending `EXPECTED_PARTNER_TABLES` there.
- Migrations are immutable once applied: mirror `bus/outbox_ddl.py` by value, never import it (`ADR-0003` Consequences, migration-immutability rule).
