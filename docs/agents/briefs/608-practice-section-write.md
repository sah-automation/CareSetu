# Brief - 608 Replace the whole-form write with a practice section write

**Ticket:** #608 · **Parent:** #599 · **Refreshed:** 2026-09-30
**Reading surface:** ~9.1K tokens (budget 10K) - within budget
**Set position:** first of the three section-write briefs in this batch (#608, #609, #610). Read-list items 1-4, 7 and 10 are the same anchors in all three, so a reader moving between the siblings sees one set of seams, described the same way each time.

## Scope

A doctor can name themselves and the clinic they practise at, pick the specialties they actually practise, and state their years of experience - and save that independently of everything else on the page. This is the first of four section writes; it carries the existing per-doctor idempotency-key scoping, the row-locked active-doctor recheck and the standard error envelope.

### Acceptance criteria

- [ ] A practice section write accepts full name, clinic name, a multi-valued specialty selection validated against the closed list, and years of experience, and touches only its own columns.
- [ ] The write is scoped per doctor for idempotency keys and rechecks that the doctor is active under a row lock, exactly as the whole-form write did.
- [ ] A non-active doctor and a non-doctor partner are both refused, and a value outside the specialty closed list is refused with a field-level detail in the standard validation envelope.
- [ ] The route layer suite asserts the write returns 200 and forwards its body verbatim, and the facade suite asserts it touches only its own columns.
- [ ] The read view now carries the new fields, so the profile read the console already performs returns them.

- **Judgement call - where specialty is read from.** `DoctorProfileView.specialty` today is a single nullable string outer-joined from the **directory entry**, and nothing at runtime ever writes it, so it is always null. #606 gives the profile row a real multi-valued specialty column and #607's shared refresh copies the values into the directory entry. Your write's source of truth is the profile row, so the read view should source specialty from there too and return a **multi-valued** field. Make that decision explicit in the closing comment, because it is the thing #612's overlap-search and #613's public-profile fields will build on. If you keep the join and widen it instead, the read view can disagree with the row that was just written the moment the refresh and the profile write land in different transactions.
- **Judgement call - what `full_name` writes.** There is no `full_name` column and no `clinic_name` column today. The single `practice_name` column is nullable, 120 characters, and is the only display name - registration fills it with the doctor's own name. Keep the column and rename the **wire** field: the practice write's `full_name` writes `practice_name`, and `clinic_name` writes the new #606 column. Note that the directory search's free-text `query` matches `partner_profiles.practice_name` with a case-insensitive `ilike`, so the doctor's own name remains what a patient can search by - that behaviour is unchanged and must stay.
- **Judgement call - the read view is a breaking response change.** The read view is declared `extra="forbid"` and consumed by the doctor API client, which carries its own `DoctorProfileView` interface and a shape guard. Widening `specialty` to a multi-valued field is a breaking change for every consumer. That is intended by the parent ticket, and the consumers (#612, #613, #617) are sequenced after this one. Say so in the closing comment so a later reviewer does not read the stale frontend interface as a defect introduced here.
- **Relevant ADRs.** `ADR-0003` (db-per-module isolation) is the one that binds this slice: the partner module owns the `partner` schema, a migration never imports current source, and the MOD-012 doctor console is a facade-only seam that owns no schema and composes other modules' facades only - which is why your route imports `PartnerFacade` from app state and the partner facade, and never the schema. `ADR-0012` (directory entry is one row per partner identity, with a doctors-only closed specialty pick-list) is what makes specialty a closed list at all. `ADR-0011` (credential expiry, lazy-on-read correctness, "tick gone = card gone") is the invariant your write must not disturb: profile fields are **declared**, credentials are **verified**, and nothing in the practice write touches credential state or the derived `verified` flag. `ADR-0006` (the facade split) explains why the doctor-profile methods sit on the partner coordinator rather than in a doctor-owned module. `ADR-0008` (the partner verification gate) is the reason the active-doctor recheck exists at all. #622 writes the two new ADRs for this batch - `0021` (a profile save moves the public directory position) and `0022` (the practice position is a PIN centroid, not a geocode) - following the highest existing number, since two files already share `0004`.
