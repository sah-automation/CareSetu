# Brief - 603 Pin the pure PIN-resolution and display-address decisions

**Ticket:** #603 · **Parent:** #599 · **Refreshed:** 2026-09-30
**Reading surface:** ~6.0K tokens (budget 10K) - within budget
**Set position:** the smallest brief in this batch, and the one with no blocker. It writes two pure functions and no schema, no route and no facade method. Its two products are read by #609 (the address section write) and nothing else in the batch touches them.

## Scope

Two pure decisions decide whether an address save can proceed and what every existing reader of the practice-address column sees. This ticket pins both with no database: a PIN is either resolved or it is not - no coarse fallback, no default position, because a silently misplaced doctor is worse than a blocked one - and the display address string is assembled from the structured parts with the optional landmark handled correctly.

### Acceptance criteria

- [ ] A known PIN resolves to a centroid; an unknown but well-formed PIN does not resolve; a malformed PIN does not resolve.
- [ ] The display address string is built from the structured address parts in a defined order, with the optional landmark present when given and absent without leaving a stray separator.
- [ ] The decision functions take their inputs and return their answers with no database, engine or facade involvement, so a unit suite can pin them without one.
- [ ] The decision that a save resolves outside the peri-urban belt succeeds with a warning rather than failing - the belt boundary is a parameter of the pure decision, not a module constant buried in a query.

5. **`tests/unit/test_credential_validity.py` - the pure-tier suite shape.** Its module docstring states the split you are copying: the SQL predicates are integration-tested through the existing partner suites, and _this_ suite pins the pure domain logic those predicates mirror. 6. **`modules/partner/shared.py` - `DEFAULT_SERVICE_AREA_NAME`, and `insert_registered_profile` with `resolve_service_area` above it.** Two facts you need. First, `DEFAULT_SERVICE_AREA_NAME` is the **vocabulary name** ("Daltonganj") that the service-area table is seeded with - it is _not_ a coordinate, and the parent ticket demotes that vocabulary from user-facing. Do not reach for it when you need the belt's centre point. Second, `insert_registered_profile` is the writer of the `practice_address` column that your display-address function's output will eventually share: its `.values(...)` payload shows the pre-structured value registration writes today (the city name typed at sign-up), and the whole function runs inside the caller's transaction with the outbox envelope in the same transaction. That is the existing writer the retained display column keeps. `resolve_service_area` immediately above is the one resolution helper in the module, and it is instructive precisely because it is **not** pure: it takes an `AsyncConnection` and queries the vocabulary. Your two functions are the counter-example, and the contrast is the argument for the seam. ~0.9K tokens.

7. **`modules/partner/directory_facade.py` - the three module constants, `_haversine_km`, and the belt clamp inside `search_directory`.** `PERI_URBAN_RADIUS_KM` (25.0), `DALTONGANJ_LATITUDE` (24.04) and `DALTONGANJ_LONGITUDE` (84.07), each with the comment recording why it is a single test-visible source. Then `_haversine_km(latitude, longitude)`, which is the crucial finding: **it returns a SQLAlchemy expression, not a number.** It builds `func.radians` / `func.power` / `func.sqrt` / `func.asin` over the directory entry's own coordinate columns and multiplies by the 6371 km mean Earth radius. The distance the belt clamp uses therefore only exists inside the database, and `search_directory` only ever compares the resulting expression against `PERI_URBAN_RADIUS_KM` by adding a `distance_km <= PERI_URBAN_RADIUS_KM` condition. There is no pure-Python kilometre distance anywhere in the backend. That is exactly why the ticket says the belt boundary must be a _parameter_ of the decision and not a module constant buried in a query: a decision you cannot evaluate without a database is not a decision you can unit-test at the boundary. ~1.2K tokens.

8. **`modules/partner/domain/exceptions.py` - the two typed-error precedents, `ProviderProfileNotFoundError` and `ServiceAreaNotFoundError`.** Read these for the shape of a decision that has to refuse: both subclass the module's `PartnerError` base, both take the offending value as a constructor argument and carry it as an attribute, and both have a docstring that states the rule being enforced and the status the adapter maps them to. `ServiceAreaNotFoundError` is the closer analogue, because it is the existing "an id was declared, it does not exist, refuse rather than attach a dangling reference" decision. You may need an unresolvable-PIN error here; there is not one today. ~0.2K tokens.

- **Judgement call - whether the display function can be called before the structured parts exist.** It must be safe to call with every part absent, because the retained display column is still written by registration as the pre-structured value until the structured parts are present, and #609 assembles the string only when they are.
