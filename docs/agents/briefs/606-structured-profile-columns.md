# Brief - 606 Add the structured profile columns and multi-valued specialty storage

**Ticket:** #606 · **Parent:** #599 · **Refreshed:** 2026-09-30
**Reading surface:** ~9.9K tokens (budget 10K) - within budget, with almost no slack
**Set position:** the expand side of the schema change, and the ticket every later backend ticket in this batch is written against. It has no blocker in its own body, but two of its decisions reach forward into #612 and #613, and one of them reaches backward into a live client. **Read the three "Judgement call" notes in the handoff before you write the first line of the migration - they are the whole risk of this ticket, and all three are structural, not cosmetic.**

## Scope

The profile gains the shape the redesign needs: clinic name, a multi-valued specialty column, the structured address parts, multi-valued consulting days and consulting hours, alongside the existing display address column that becomes a backend-assembled projection. Latitude and longitude stay stored and not null, but become server-written only - the update schemas no longer accept them. Existing doctor rows upgrade cleanly, with the two never-reliably-structured free-text fields reset to empty rather than guessed at.

### Acceptance criteria

- [ ] The partner profile table gains clinic name, a multi-valued specialty column, address line, address landmark, address locality, address city, address PIN, a multi-valued consulting days column and consulting hours, all nullable or defaulted so existing rows upgrade cleanly.
- [ ] The existing availability column is superseded by consulting hours, and the free-text languages column is replaced by the closed vocabulary shape.
- [ ] The existing practice address column is retained and documented as a denormalised display projection of the structured address parts - still written by registration as the pre-structured value until the structured parts are present, so registration and its four read sites keep working unchanged.
- [ ] The directory index specialty column widens to multi-valued and its check constraint is dropped, replaced by application-level validation against the closed list.
- [ ] Latitude and longitude remain not null in the database but are removed from every update schema, so a client can no longer supply them.
- [ ] Existing doctor rows are migrated with languages and consulting days reset to empty and specialties normalised to empty - never parsed out of the old free text.
- [ ] Years-of-experience bounds tighten to a realistic range, and the repository up-and-down round-trip passes with a single migration head.

## Handoff notes

- **No blocker in the ticket body, but a soft ordering coupling with #602 (own the closed vocabularies for specialty, languages and consulting days).** #607's body names #602 as a blocker and #606's does not, so formally you may land first - and if you do, the column _types_ must be the ones that survive #602. #602 lands roughly twenty specialty values, a scheduled-languages-of-India list, a seven-day consulting-day list, and one validation entry point per vocabulary that a multi-valued selection is checked against member by member. So: the profile's specialty column, its consulting-days column and its reshaped languages column should all be the same multi-valued storage shape, because that is the only shape a closed-list validator can be applied to without re-deriving a parse. If #602 has already landed when you start, match its shape exactly rather than assuming the shape you find in the tree.
- **Judgement call 1, and the largest risk in this ticket: widening the directory entry's specialty column breaks three live readers that #612 and #613 do not own.** The column is `String(40)` nullable with a doctors-only check. Three places read it today, and none of them is yours to change: (a) the directory sub-facade's `search_directory` specialty predicate, which is **equality** (`directory_index.c.specialty == specialty`) plus a `partner_type == "doctor"` pin; (b) the directory sub-facade's `get_provider_profile` mapper, which does `str(row.specialty)`; (c) `PartnerFacade.get_doctor_profile`'s mapper, which does the same `str(row.specialty)` off the outer join. Changing the column to a multi-valued type makes (a) compare a JSONB column against a string, which Postgres will not do sensibly, and makes (b) and (c) pass `mypy --strict` while producing a Python list repr as the response's `specialty` string. The integration suite has a seeded-specialty helper and a case that composes type, specialty and free-text filters, and the directory unit suite pins the predicate, so both go red. Two defensible resolutions: **(a) add the multi-valued column alongside the existing single-valued one**, let #612 cut the search over and drop the old column, which keeps every reader green and costs a temporary duplicate; or **(b) fold the overlap predicate into this change** and narrow #612 to the area-from-declared-locality half, which is cleaner but takes on work #612's brief already sizes. Pick one deliberately, say which and why in the closing comment, and make the schema declaration, the migration and the readers agree. Do not leave it half-done.
- **Judgement call 2: removing the coordinate fields from the update model makes the live profile save return 422 the moment this lands.** `DoctorProfileUpdate` is `extra="forbid"`, the shipped profile page still sends `practice_latitude` and `practice_longitude` through `updateDoctorProfile` on every whole-form save, and the whole-form write is only _replaced_ by #608 and only _retired_ by #611. So between this ticket and #611, `PUT /v1/doctor/profile` rejects every save from the real client. What breaks and what does not: the two backend unit suites (`test_doctor_profile_routes.py` and `test_doctor_profile_facade.py`) **will** go red and must be updated here - the route suite asserts the body is forwarded verbatim, and the facade suite asserts the set of written columns; the frontend unit suites stay green because they stub the API client; and there is **no end-to-end coverage of the doctor profile save at all**, so nothing catches it in CI. Your three options: land the client's sender change in the same change (small - drop two fields from one object literal and two from the form state), accept a documented red window and say so loudly in the closing comment, or keep the fields on the model as ignored-for-write so the shape stays accepted. This is a decision, not an accident; make it consciously.
- **Judgement call 3: the `experience_years` bound lives in three places that must move together, and the fourth is a client.** The database `CHECK` constraint, `DoctorProfileUpdate.experience_years` and `DoctorProfileView.experience_years` (both `Field(ge=0, le=100)`) are yours. The **fourth** is the profile page's own `LIMITS` object, which enforces the range client-side - so tightening the backend below what the client allows turns a legitimate value into a silent 422 for exactly the doctors with the longest careers, which is the population the field is for. Coordinate the number with #608 and say in the closing comment which value you chose and why that value is the realistic one; "realistic range" in the criterion is a judgement and you are the one making it.

Writers: registration, through `insert_registered_profile`, which keeps writing the pre-structured value (the city name captured at sign-up) unchanged; and the new address section write in #609, which assembles the display string from the structured parts. Readers: the private doctor profile view (`get_doctor_profile`), the operator verification queue row, and the operator per-partner detail row. The public provider profile is **not** one of them - it projects `practice_name`, not `practice_address`. The column's name, type and nullability are all unchanged; what changes is that it gains a documented second writer and a documented derivation. Write that documentation in the schema declaration's column comment, because a reader arriving at a `Text NOT NULL` column with two writers and no comment will assume it is a source of truth and edit it.
