# Brief - 615 Rebuild the profile page shell: identity band, trust bands, anchor index

**Ticket:** #615 · **Parent:** #599 · **Refreshed:** 2026-09-30
**Reading surface:** ~9.8K tokens (budget 10K) - within budget

## Scope

The page stops being a single long stack of unstyled boxes. An identity band heads it - a large avatar with an in-place camera control that opens the file picker where it sits, the doctor's name as the heading, the clinic name beneath it, and a chip row carrying the verified tick and the doctor's specialties. Two visually distinct trust bands separate what CareSetu verified from what the doctor declared. A sticky anchor-chip index jumps between sections. And latitude and longitude disappear from the UI entirely - the doctor is never asked a question only a map could answer.

Acceptance criteria (from ticket):

- [ ] The page is split into a shell plus one component per section; the monolithic page component no longer renders its sections inline.
- [ ] The identity band carries a large avatar whose camera control opens the file picker in place, the doctor's name as the page heading, the clinic name beneath it, and a chip row with the verified tick and the doctor's specialties.
- [ ] The credentials and activation state render in the verified band carrying the tick; everything the doctor typed renders in the declared band, which says so in words.
- [ ] A sticky anchor-chip section index jumps between sections and holds no state - no section is hidden, and every per-section save button stays beside its own fields.
- [ ] Latitude and longitude inputs are absent from the page, and the service-area vocabulary name is no longer rendered to the doctor.
- [ ] Every new and changed string ships in both locales and the bilingual parity suite passes.

## Handoff notes

- **Three blockers, and what they will have landed.** The ticket body names them positionally; resolved against the parent's child list they are **#600** (the label/primitives ticket), **#605** (the section shell and edit buffer) and **#608** (the practice section write). By the time this ticket starts:
  - #600 will have added the card, input, textarea, badge, switch and toggle-group primitives to the frontend component library, each with a colocated suite and a header comment naming what was changed away from upstream shadcn. **The bands compose `Card*` and the identity band uses the adopted `Avatar` and `Button`; do not hand-roll a card wrapper or an avatar.** #600 also fixes the exact token paths a new primitive may reference, and its adaptation comments record which token each selected/checked state resolved to - read those before choosing a state colour.
  - #605 will have landed the section shell and the per-section edit buffer and converted this page to use them (read-list item 5).
  - #608 will have landed the practice section write, so the practice section's fields and its own save exist as a contract even though the section's **content** is #617's job. This is why the page split is safe to do here: you are splitting onto a shell and a write that are both already landed.
- **Read the anchor index's acceptance criterion as a prohibition, not a feature.** "Holds no state" plus "no section is hidden" plus "every per-section save button stays beside its own fields" together rule out three tempting things: a scroll-spy that tracks the active section, a collapse/expand behaviour that hides section bodies, and a single page-level save. A scroll-spy is state, and it is a different design with its own accessibility questions. A static chip row of in-page hash links, sticky, that moves focus, satisfies all three clauses.
- **The anchor index must target the shell's own anchor surface, not wrap each section.** If the shell #605 lands does not expose an id or anchor prop, add one to the shell rather than wrapping every section in a second element - a wrapper per section means two headings and two landmarks per section and the accessibility floor bites. If the shell has no such surface and you add one, that is a change to a landed sibling's contract: say so in the closing comment.
- **Judgement call, recorded: the trust bands are a visual grouping, not a permission boundary.** The verified band renders what the platform derived (credentials, activation state, the tick); the declared band renders what the doctor typed. The backend already owns the derivation - the `verified` flag on the projection is computed from activation state plus credential dates and is never stored - so the bands must not become a second derivation site. Read the tick from the flag; do not recompute validity in the client to decide which band a credential falls in. That is `credentialExpiry`'s job in the card, and the band's job is to place the card.
- **Judgement call, recorded: the identity band lifts `PhotoCard`'s picker rather than reimplementing it.** AC 2's "camera control opens the file picker in place" is a statement about placement and size, not about a new upload path. The existing card already gets this right: an `sr-only` file input plus a `Button` that clicks it, resolving through the shared photo-source hook (a ref-keyed module cache, owned object URLs, and two distinct failure answers - a resolved `src` of null versus an absent photo), with a fresh idempotency key per upload. Keep all of that. What you change is the surrounding layout. Re-implementing the picker is how a section silently loses the owned-object-URL cleanup.
- **Judgement call, recorded: removing the coordinates is a client-side deletion, and it is half of a two-ticket change.** #606 removes `practice_latitude`/`practice_longitude` from every backend update schema and the `area` projection. This ticket removes the two inputs, their client-side validation branches, and the `area` string from the page. It does **not** touch `DoctorProfileUpdate` or `updateDoctorProfile` - #611 deletes the whole-form write, and until then the page's remaining save still sends coordinates. Expect that transitional state and do not try to reconcile it here; the section writes (#608, #609, #610) are what make the whole-form call unreachable, and #611 is what removes it.
- **The service-area vocabulary name must stop being rendered, not just stop being an input.** `resolve_service_area` and the default `Daltonganj` label are a backend projection the page currently shows as the `area` string. The demotion of service area to a non-user-facing concept is part of this batch, so delete the render, not the label styling. Do not invent a replacement label - if the section shells need a heading for the address section, that heading is #616's, and its string is a `doctorProfile` key in both locales.
- **The tick has a specific meaning and the band must not overclaim.** Per the glossary, verified is true iff the partner is `[Active]` and every required credential is unexpired and unrevoked, and it always agrees with search visibility - "if the tick is gone, the card is gone". So the identity band's tick and the verified band's credentials must come from the **same** source state, and if the flag is false the band must not show a tick next to a stale credential list. `credentialExpiry` is the existing helper that decides validity for display; use it, and let the flag decide the tick.
- **Unresolvable names.** `locality` and `clinic name` are glossary entries this batch introduces (by #622) and they do not resolve in `CONTEXT.md` today. This ticket is their first consumer on the doctor surface, so you will be writing copy against vocabulary the glossary does not carry yet. Do **not** add the glossary entries from here - #622 owns the file. Use the words, and flag any place the wording felt wrong in the closing comment. Likewise `declared` as a term is new; the band must **say so in words** (AC 3), which is a copy requirement, not a new domain concept.
- **New strings are more than the band's labels.** Everything this ticket adds is a new `doctorProfile` key: the band labels, the tick chip's accessible name, the anchor labels, the camera control's accessible name, the section titles, and the shell's generic save/saved/retry copy if #605 has not already added it. The parity suite fails on any key present in one locale and missing from the other, so add both branches in the same edit. The Hindi strings are not placeholders - the blueprint's parity rule and §1.3's Devanagari line-height rule both apply.
- **The design-token gate is a test, not a review convention.** A literal colour in a class attribute fails the frontend suite; the tokens stylesheet is the single hex source and the Tailwind theme maps CSS variables only. The two bands need to be _visually distinct_, and the answer is existing token vocabulary (the `accent`/`accent-soft`/`accent-strong` group, the `txt`/`txt-muted` group, the trust-cue colours in §1.6) - not a new hex, and not a raw `bg-[#...]` arbitrary value.
- **Accessibility floor applies from the first commit.** §9.4 is a hard floor: labelled controls (no placeholder-only labels), visible focus, touch targets >= 44px, status messages announced, `prefers-reduced-motion` honoured. The page suite's **axe scan is #617's** and is explicitly not this ticket - but do not knowingly introduce a violation for it to find. If a band rendering decision turns ambiguous, §9.4 and §9.5 are the tiebreakers.
- **Relevant ADRs.** **ADR-0011** (credential expiry, lazy-on-read correctness, "tick gone = card gone") is the invariant behind the verified band: profile fields are **declared**, credentials are **verified**, and the band's split is exactly that distinction made visible. **ADR-0020** (profile media storage) is why the photo is an opaque ref resolved through the shared resolver rather than a URL - the identity band takes a resolved source, never a stored ref. **ADR-0012** (one directory entry per partner identity, doctors-only closed specialty pick-list) is why specialty is a closed list the chip row renders rather than free text. **ADR-0005** is the cookie/localStorage session decision behind the doctor shell this page sits in. The two ADRs this parent work writes are reserved as **0021** and **0022** and are owned by **#622**; neither constrains a frontend shell and neither blocks this ticket.
