# Brief - 607 Extract the shared directory-entry refresh operation

**Ticket:** #607 · **Parent:** #599 · **Refreshed:** 2026-09-30
**Reading surface:** ~9.7K tokens (budget 10K) - within budget, with very little slack
**Set position:** the last of the three briefs in this batch and the one with the highest security stakes. It has two upstream blockers, and its whole reason for existing is that a doctor must be able to move their own listing **without** being able to activate themselves or influence their own credential validity. The "Judgement call 1" note in the handoff is the shape of the function; the "Judgement call 2" note is a cache bug that will otherwise make the ticket's own criterion unverifiable.

## Scope

The directory entry is currently written in exactly one place - the operator approval path - so a doctor editing their own profile cannot move their listing. This ticket lifts that write out of the activation transition into one shared operation, called by both operator approval and the doctor's own address save, which refreshes only the position, the specialties and the locality. The listed flag and every part of the verified derivation stay untouched, structurally, not by convention.

### Acceptance criteria

- [ ] One shared directory-entry refresh operation is called by both the operator approval path and the doctor address write - the duplication is gone.
- [ ] The refresh writes only the position, the specialties and the locality, and the listed flag and every verified derivation are provably untouched.
- [ ] Re-running the refresh on a doctor who already has a directory row updates that row rather than inserting a second one.
- [ ] The listed flag and credential-validity non-interference is asserted at the facade seam and again at the integration seam.
- [ ] The existing directory-backfill integration suite and the activation integration suite still pass unchanged.

## Handoff notes

- **Blockers, both upstream, and both about the columns you write rather than the mechanism you extract.** The ticket's own "Blocked by" section names the closed-vocabularies ticket (internal `#3`, GitHub **#602**) and the structured-profile-columns ticket (internal `#7`, GitHub **#606**). Do not start before both land. #602 lands roughly twenty specialty values, a scheduled-languages list, a seven-day consulting-day list, and one validation entry point per vocabulary. #606 lands the profile columns the refresh reads: the multi-valued specialty column, the structured address parts, and the PIN centroid table #601 created - and it decides the **shape and name of the specialty column you are about to write into the index row**, which is a real dependency and not a formality. If either is unlanded when you read this, the correct action is to stop, not to guess the column name. Nothing in this ticket is blocked on #601, #609, #612 or #613, though #609 is your second caller and lands after you.
- **Judgement call 1: the strongest answer to "provably untouched" is to have nothing to pass.** The criterion says the listed flag and every verified derivation are **provably** untouched, and there are two ways to achieve that. (a) Take the values as parameters - position, specialties, locality - and simply omit the flag from the signature and the `set_`; the proof is then a code review of a short signature. (b) **Keep today's shape: take only `(connection, partner_id)`, and let the operation read the profile row itself with the same `from_select` it uses today.** With (b) there is no parameter a caller could abuse, the profile row is the single source for every refreshed value, and the `#609` address save gets the new position for free because it has already written the profile in the same transaction before calling. (b) is what the code already does and it is the better answer; take it unless you have a concrete reason not to. Whichever you take, the `is_active` write has to **move out of the shared operation and stay at the activation call site**, which means `activate_partner` keeps a small residual write (or a flag on the shared call, which is the weaker design) - make that split explicit in the code and in the closing comment, because the alternative is a doctor address save able to set `is_active = true` on a row whose partner is not active, and `is_active IS TRUE` is one of the four AND-ed clauses of `provider_visible`.
- **The `partner_type` column is a third thing the current code writes that criterion 2 does not list.** Today's `set_` writes five columns: position, `partner_type`, `is_active` and `updated_at` (and, once #606 lands, specialties and locality). The criterion names position, specialties and locality only. So `partner_type` needs a decision, and the safe one is to move it out with `is_active` - partner type is a registration-time declared attribute, not a doctor-editable field, and letting a profile save re-derive it means a doctor editing their profile could in principle change their own type. Say in the closing comment that `partner_type` was excluded on the grounds that it is not in the criterion's set, so a reviewer sees the choice rather than the omission.
- **The `specialty` half is a behaviour change dressed as a move, and it is asymmetric between insert and conflict.** Today `specialty` is in the insert column list but sourced from `literal(None)`, with a docstring note that no specialty data exists in the profile yet; and it is **absent from the `on_conflict_do_update` set**, so the conflict path has never refreshed it. After #606 lands, both halves have to carry the real value - insert from the profile, conflict in the `set_` - and a doctor who **already** has a directory row will only get their specialty populated by a refresh, not by the insert. That is why criterion 3 ("re-running the refresh on a doctor who already has a directory row updates that row rather than inserting a second one") is the load-bearing half: without the conflict-side `set_` change, every existing doctor stays specialty-less in the index forever. The multi-valued storage shape #606 lands makes the membership question yours to state: either you keep the column's value in the index denormalized from the profile, or you widen it and let #612's overlap predicate read the multi-valued form.
- **Judgement call 2, and it will make criterion 5 look green while the feature does not work: the search cache stores the doctor's distance and does not re-derive it.** `_cached_search_view`'s docstring is explicit - on a hit the cached items are **served as-is** because "their geo/distance already match the cached key", and the only re-derivation permitted on a hit is the visibility tick for the cached ids. The cached key contains the **caller's** (patient's) geo point and the filters, never the doctor's own position. So a doctor who saves a new address and whose cached search row survives gets the **old** `distance_km` served until the TTL expires - the nearest-first ordering and the "how far away is this doctor" number are both stale, while `is_active` and the credential checks are correct. The visibility tick being re-derived is exactly what makes this easy to miss: your test asserting "the listed flag is untouched" passes while the position is silently not reflected. Two options: flush the namespace on a position-only refresh (the outer wrapper in item 10, which is a best-effort Redis delete and is silent on failure - so the failure mode is "stale for one TTL", which the ADR-0011 lazy-correctness posture already accepts elsewhere), or leave the flush out and accept the staleness window. **The first is the honest answer**, because #609's whole point is that the doctor's saved address is what the next search reflects; the second is defensible only if you write the staleness down. Whichever you pick, extend the docstring that enumerates the two events firing the flush, and note that the `directory_visibility_changed` name is now a slight misnomer for a position-only change.
- **What must stay in `activate_partner`, and why it cannot move.** The credential `verified` stamp is round-scoped and the refresh has no round to scope by, so it cannot move; it also belongs to the activation transition because re-approving a later round must never touch an already-approved round's history, and revoked rows must be left alone. Keep the approval path's five-step order exactly as item 9 has it: transition, decision row, activate, event, cache flush. Keep the whole thing inside the caller's transaction, which is what the `activate_partner` docstring already says when it cites the outbox ADR - the refresh takes an `AsyncConnection` and runs in the caller's transaction, and that is the reason a doctor address save can write the profile and then refresh the index atomically without a second transaction. Do not give either operation its own `engine.begin()`.
- **Migration mechanics, and the assertion that is not yours to grow.** No migration ships in this ticket. But the integration seam runs the real migration chain, so your tests must tolerate whatever head exists when you run - this batch has four other schema-touching siblings, and if #606 has landed (it must have) the partner schema is wider than when the baseline was recorded. If a new integration test inserts a profile row, insert every column as nullable-or-defaulted so it keeps working as the schema grows.

- **Relevant ADRs.** `ADR-0011` (credential expiry, lazy daily sweep) is the governing one: it makes the cache an accelerator rather than a correctness surface, which is what makes the stale-distance question in judgement call 2 a latency bug rather than a correctness bug - and it is the ADR you cite when you decide the staleness window is acceptable. `ADR-0012` (the directory entry is one unit per partner) is the decision you are **extending**: it records that the entry's fields are activation-owned, and criterion 2 amends exactly that, so note in the closing comment whether ADR-0012 needs an amendment; #622 owns the documentation change and cannot know to make it unless you say so. `ADR-0008` (the two-step verification gate) explains why approval is the only path to `Active` and therefore why `is_active` must stay behind that path. `ADR-0002` (the transactional outbox) is why the refresh runs inside the caller's transaction rather than opening its own, and why the approval path's `partner.activated` envelope is unaffected by your extraction. `ADR-0003` (db-per-module isolation) binds the blast radius only: your operation stays in the partner module, reads one of its own tables, and adds no foreign key. #622 writes the two new ADRs for this batch - **`0021`** (a profile save moves the public directory position, superseding the earlier decision that a private save must not move the practice pin) and **`0022`** (the practice position is a PIN centroid rather than a geocode) - following the highest existing number rather than the count of files, since two ADR files already share `0004`. **ADR-0021 is the direct parent of your ticket**: it is the record of the decision that a doctor editing their profile _does_ move their listing, and this ticket is that decision becoming code. If your extraction is shaped differently from what ADR-0021 will say, that is worth knowing before #622 writes it.
- **A naming note for #609.** Your new operation's name becomes the API that #609's address write calls, and #612/#613 never call it. Pick a name that says it refreshes the **read-side projection** and not that it activates or indexes a partner - the whole security argument of this ticket is that a doctor-triggered call cannot read as a privilege escalation to the next person who opens the file. Similarly, if you add a method to `CredentialValidityPort`, the doctor's address save will reach it through that port, which is a slightly odd fit (the write is not about credential validity) and worth a comment saying so rather than a second port with one method.
