# Brief - 612 Make specialty search an overlap match and serve area from declared locality

**Ticket:** #612 · **Parent:** #599 · **Refreshed:** 2026-09-30
**Reading surface:** ~13.1K tokens (budget 10K) - OVER; drop read-list items 5, 3 and 10 (and trim item 1) to land at ~9.8K

## Scope

Three patient-facing surfaces are silently returning nothing today because no specialty has ever been written. With specialties real and multi-valued, filtering the directory by specialty returns results again, the homepage chips and the pick-a-doctor suggested-specialty pre-filter return results again, and a doctor's listing shows every specialty they practise rather than one. The area on a search result becomes the doctor-declared locality instead of the platform's service-area vocabulary, which stops showing every doctor as Daltonganj.

AC:

- [ ] The specialty filter is an overlap match against the multi-valued column rather than an equality match, and still pins partner type to doctor.
- [ ] A doctor with two of the three requested specialties appears in the filtered results, and a doctor with no specialties still appears in an unfiltered search.
- [ ] The search result area is served from the doctor-declared locality and the read path no longer joins the service-area vocabulary table.
- [ ] The service-area vocabulary table, its seeded row and its column all remain, because registration still resolves them - they simply stop being rendered to users.
- [ ] The pick-a-doctor flow's unit test is reviewed for whether it proves the real query rather than mocking the directory client, and the answer is recorded.

This is a **live-defect fix**, not a feature. The predicate is one expression; the cost is in the surface you must not break while changing it.

## Handoff notes

**Blockers, and what they will have landed by the time you start:**

- **#602** (own the closed vocabularies for specialty, languages and consulting days) - gives the specialty pick-list a single owning home instead of the two places it lives today (the `Specialty` string enum in the partner credential domain module, and the doctors-only check constraint on the directory index). The overlap predicate must validate its argument against that owned list; the directory route adapter's `Specialty` query type should come from the same home.
- **#606** (structured profile columns and multi-valued specialty storage) - the substrate. It widens the directory index specialty column to multi-valued and **drops its check constraint** in favour of application-level validation, adds the address parts and the clinic name, and replaces the free-text `languages` and `availability` columns. Its migration resets existing rows' specialties to empty rather than parsing them out of old free text, so after it lands every existing doctor has an empty specialty set and the "no specialties" half of AC 2 is the real-world default, not an edge case.
- **#607** (extract the shared directory-entry refresh operation) - the only runtime writer of the directory entry after this batch. It refreshes position, specialties and locality, is called by both the operator approval path and the doctor's own address save, and provably cannot touch the listed flag or any part of the verified derivation. **This is what makes the fix reachable:** until #607 lands, nothing writes a specialty at runtime and the overlap predicate matches against an always-empty column. Its integration suite is the natural place to see a real multi-valued specialty row; if you need one before #607 lands, extend the existing `_seed_specialty` raw-SQL helper in the search suite rather than inventing a new fixture.
- #612 does not depend on the section-write tickets; it is a read-path change and can be sequenced independently of #608/#609/#610.

**Judgement calls made while mapping this surface:**

- **Keep the request side scalar.** AC 1 says the _filter_ is an overlap match against a multi-valued column. The natural reading is: the caller still asks for one specialty (a single `Specialty` query value from the closed list, exactly as the route adapter types it today), and the column holding the doctor's full set is what gets overlapped. That keeps the homepage chips, the directory browse facets, the pick-a-doctor pre-filter and the wider-area fallback contract all unchanged, and keeps the cache key a scalar. Do not widen the request to a list in this ticket.
- **The projection is a separate decision AC does not settle.** Whether `DirectoryEntry.specialty` becomes a list is not in the acceptance criteria. The ticket's "What to build" wants a doctor's _listing_ to show every specialty, but that is the browse surface's rendering, which is owned by a frontend sibling. My recommendation: keep `DirectoryEntry.specialty` scalar in this ticket (a representative value) and raise the widening as an explicit follow-up, because widening it forces edits to the frontend `DirectoryEntry` interface, its `isDirectoryEntry` shape guard, and the `SPECIALTY_LABEL_KEY` map that is **copy-pasted in five places** with its own class factory each. If you do widen it, that is a separate, larger slice - say so rather than absorbing it here.
- **The area change is a join removal, not a vocabulary change.** The read path's `outerjoin` to the service-area table and its `DEFAULT_SERVICE_AREA_NAME` fallback in the view builder are both removed together; the projection reads the declared-locality column and nothing else. Registration keeps calling `resolve_service_area`, the table keeps its seeded row, and `partner_profiles.service_area_id` keeps its column and its nullable-with-no-FK shape (ADR-0003 isolation). A doctor who declared no locality must render a null area, not a substituted vocabulary row name - the frontend card already filters non-null meta before joining, so a null area renders cleanly with no client change.
- **The "pin partner type to doctor" clause is load-bearing and must survive.** Because the column widens, a lab or chemist row could now carry an array. Keep the explicit `partner_type == "doctor"` condition alongside the overlap; never rely on "labs carry no specialty" as the mechanism. The existing integration test that asserts a lab-plus-specialty request matches nothing is the proof.
- **AC 5's answer, already determined from the live tree:** the pick-a-doctor suite does **not** prove the real query. It replaces the directory client's `searchDirectory` with a bare `vi.fn()`, returns a hand-built item list regardless of arguments, and asserts only that the page invoked the client with a `specialty` of the derived value. It is a correct test of the page's argument and a vacuous test of the filter, which is why it stayed green while production returned nothing. Record that finding; do not try to fix the frontend suite's mocking here, because the honest fix is a backend integration test asserting the overlap query, which is exactly what the directory search suite gives you.
- Relevant ADRs: **ADR-0011** (credential expiry, lazy-on-read plus daily sweep) is the reason visibility is derived on every read and never cached as a trust flag, and it is why the wider-area fallback may relax location without relaxing anything else. **ADR-0012** (directory entry unit per partner) fixes the one-entry-per-partner shape this ticket projects from. **ADR-0003** (db-per-module isolation) is why the service-area vocabulary table carries no foreign key from the profile and why removing a join is legal without a schema change. **ADR-0006** (iam facade split) is not in scope here.
