# Brief - 616 Build the address section card

**Ticket:** #616 · **Parent:** #599 · **Refreshed:** 2026-09-30
**Reading surface:** ~7.7K tokens (budget 10K) - within budget

## Scope

The address becomes an address. Building and street, an optional landmark, a locality, a city and a 6-digit PIN code - and district and state shown back read-only, derived from the PIN, so a mistyped PIN is visible before saving rather than after. A PIN that cannot be resolved fails inside this card with the error under the PIN input, and every other section keeps working while it is fixed.

Acceptance criteria (from ticket):

- [ ] The card renders building and street, an optional landmark, locality, city and a 6-digit PIN code, and no coordinate input.
- [ ] District and state render read-only, derived from the PIN, and are visible before the save is submitted.
- [ ] An unresolvable PIN renders the field-level error under the PIN input and the rest of the page's unsaved edits survive it.
- [ ] A PIN resolving outside the peri-urban belt warns the doctor before saving that their listing will surface as an outside-your-area result, and the save still succeeds.
- [ ] The card saves on its own, with its own pending, saved and retry states, and its buffer is not reseeded by another section's answer.
- [ ] Unsaved changes in this card are guarded before navigating away.
- [ ] Every new string ships in both locales and the bilingual parity suite passes.

## Handoff notes

- **Two blockers, and what they will have landed.** The ticket body names them positionally; resolved against the parent's child list they are **#605** (the section shell and edit buffer) and **#609** (the address section write). Transitive and worth knowing: **#603** (the two pure PIN-resolution and display-address decisions), **#606** (the structured address columns and the removal of the coordinate fields from every update schema), **#607** (the shared directory-entry refresh the write calls) and **#601** (the PIN centroid table). By the time this ticket starts, all of those have landed and item 7 is a read, not a build. #608 (the practice write) is the closest in-batch precedent: same route registration site, same doctor guard, same `run_idempotent` per-doctor namespace, same row-locked active-doctor recheck, same facade read-back. Read #608's brief first if you have not.
- **The gap that makes this ticket more than a form: `ApiError` throws away `details`.** The shared error module's `ErrorEnvelope` declares `details: Record<string, unknown>` and the `ApiError` constructor keeps only `code` and `traceId`. The 422 shape #609 lands - `details.errors` as a list of `{path, reason}` with `path` naming the PIN field - is the _only_ thing that lets you render the error under the PIN input instead of guessing which input failed, and today it does not survive the throw. Widening `ApiError` to carry `details` (or a typed field-errors accessor) is therefore **in scope for this ticket**, not a nice-to-have. Before you widen it, grep every construction and narrowing of `ApiError` across the frontend: it is a shared module and a type change there is a whole-app change, which is why the strict typecheck is in done-verify. Whatever shape you add, assert it in a test - a `details`-preservation test in the shared error module's own suite, not only in the card.
- **Judgement call, recorded: the belt warning is pre-save, comes from the last answer, and never blocks.** AC 4 says the doctor is warned **before saving** and that the save **still succeeds**. So the warning is a non-blocking notice, never the `role="alert"` invalid-field line, never a client-side validation that refuses submit, and never a `4xx`-style error. The belt boundary is a **parameter** of the pure decision #603 pins, and the client has no access to the centroid data behind it, so the client **cannot compute the warning**. The honest shape: the warning renders from the last write answer that carried it, and before the first save the card simply has nothing to warn with. Render that as an absent notice, not as a spinner and not as an empty promise. If the product wants a pre-save warning on a PIN the doctor has never saved, that needs a resolve-on-blur endpoint the ticket does not add - say so in the closing comment rather than inventing the endpoint.
- **Judgement call, recorded: district and state before first save are empty, and that is not a gap you can close in the client.** AC 2 wants them visible before the save is submitted "so a mistyped PIN is visible before saving rather than after". The client cannot derive them: PIN-to-centroid resolution is a server pure decision (#603) over a seeded table (#601), and there is no resolve endpoint on the doctor API client. So they render **read-only from the last saved answer**, and the first time a doctor types a new PIN they are empty until the save answers. Render empty read-only values with their labels intact - do not disable the field, do not put a spinner over an input the doctor is actively typing into, and do not call an endpoint the ticket does not add. This is the one acceptance criterion whose literal reading needs a backend capability that is not in the batch; implement the honest version and flag the gap.
- **Judgement call, recorded: the unsaved-changes guard is new in this repo.** AC 6 is the first navigation guard in the tree - nothing else in the frontend has one. Use the platform `beforeunload` event for the browser-level prompt, registered and removed with this card's dirty flag, and pair it with whatever in-app navigation interception the doctor shell already provides (the app-shell's nav config and the account menu are the surfaces a doctor can leave through). Do **not** build a router-level interception that the doctor's other pages would silently bypass - a guard that only works on a full page reload is better than one that is inconsistently applied. Two locales for the prompt copy if the platform allows it, and remember that `beforeunload` prompts are browser-owned strings the app cannot style or translate on most browsers, so do not build a translated string you cannot control.
- **AC 3's survival guarantee is the identity guard, and it is easy to break in the failure path.** "The rest of the page's unsaved edits survive it" is guaranteed by the seed key being the whole answer object **and** by the failure path adopting nothing. Make sure a rejected write does not call the adopt seam, does not clear its own dirty flag, and does not write anything back into the shared source. The existing whole-form save already sets the precedent of deliberately not clearing dirty on success; the failure path is where the same reasoning is most likely to be skipped.
- **This card is the only one that gets a field-level error, and the field-level scope is the shell's, not a card-local invention.** §9.1 names four scopes; field-level is "inside forms, under the input", inline is "card/row-scoped, quiet retry link in place", banner is page-level and dismissible with a short `trace_id`, and toast is transient. The unresolvable PIN is field-level and belongs under the PIN input. Wire it through the shell's error presentation with `aria-describedby` on the input and an assertive live region on submit failure (§9.4), and keep the `role="alert"` invalid-field line for client-side validation failures so the two do not compete.
- **Map the `details` path to the input by name, and fall back honestly.** §9.5 says a `details[]` entry maps `path` to a field and an unmapped path falls back to the form summary. #609's `path` names the PIN field; your form field names must line up with it, so read the request model's field names before you write the mapping. An unmapped path must land in the form summary block, not be dropped and not be guessed onto the nearest input. The summary block also has obligations from §9.5: it moves focus to the first invalid field and announces the error count.
- **An unresolvable PIN is an expected client error, and that is a deliberate product decision, not an oversight.** AC 6's sibling in #609 is explicit that the data gap is a follow-up and must not be silently worked around - there is **no support-request surface anywhere in the repo** (`partner_verifications` is a credential-review queue, not a support queue), so the field-level error is genuinely all the doctor gets. Do not invent a fallback position, do not write a row into any queue to compensate, and do not soften the copy into something that sounds temporary. The copy is calm, specific and actionable (§9.5's expected-`4xx` rule), and the action is "correct the PIN".
- **The `path` plus `reason` list is the shape; do not invent a second error format.** §2 of the API standard is one envelope for every error, and `details` is where validated field errors live. If you find yourself modelling the PIN failure as a bespoke `{pin: string}` body, you have broken the envelope. Extend `details`; do not add a field beside it.
- **Unresolvable names.** `locality` is named in the ticket body and is a glossary entry this batch introduces (by #622); it does not resolve in `CONTEXT.md` today. Use the word, do not add the glossary entry from here. The service-area vocabulary name is **not** rendered in this card either - it was demoted to a non-user-facing concept, and #615 is what removes the last render of it. If the card needs a heading or a locality label, both are new `doctorProfile` keys in both locales.
- **New strings are more than the field labels.** Field labels and help text, the two read-only derived labels, the field-level PIN error, the belt warning, the form summary block, and the section title are all new keys in **both** locale branches. The parity suite fails on any key present in one and missing from the other, so add both in the same edit; the Hindi is not a placeholder (the blueprint's parity rule and §1.3's Devanagari line-height rule apply). The `path` values the backend returns are **not** user-facing copy - they are field identifiers, and the doctor never sees a raw path or a raw code (§9.5).
- **Relevant ADRs.** **ADR-0012** (one directory entry per partner identity, one geo point, doctors-only closed specialty) is why there is exactly one PIN and one derived position and no second row. **ADR-0011** (credential expiry, lazy-on-read correctness, "tick gone = card gone") is the invariant the write must not disturb: **a profile save must never change the listed flag or any credential-validity derivation**, so a doctor cannot activate themselves by editing their address - your card must not offer any affordance that implies saving an address changes their listing status. **ADR-0022** (the practice position is a PIN centroid rather than a geocode, with the rejected alternatives) is written by **#622** and is exactly this ticket's premise - if your rendering decisions make a choice the ADR text will have to record, say so in the closing comment. **ADR-0021** (a profile save moves the public directory position, superseding the earlier decision that a private save must not move the practice pin) is why the belt warning's copy has to say the listing will surface as an outside-your-area result rather than saying the address is invalid. **ADR-0003** (db-per-module isolation) and **ADR-0006** (the facade split) explain why the write lives on the partner coordinator and why your card's call reaches it through the doctor API client rather than a schema. None of these constrain a frontend card directly; they constrain what the write it calls is allowed to have done.
