# Brief - 605 Extract the reusable profile section shell and a per-section edit buffer

**Ticket:** #605 · **Parent:** #599 · **Refreshed:** 2026-09-30
**Reading surface:** ~9.6K tokens (budget 10K) - within budget

## Scope

The redesigned profile page has four independently saving sections, and the page already carries the discipline that makes an in-flight edit safe - seed once per distinct server answer, never reseed a dirty buffer, never let a save's own reply discard keystrokes. This ticket lifts both into reusable form: a section shell owning title, help text, dirty state, its own save button, pending state, saved confirmation and error presentation with retry, and an edit buffer per section. The current page is converted to use them, so nothing is shipped as dead code.

Acceptance criteria (from ticket):

- [ ] A reusable section shell owns title, help text, dirty state, its own save button, its own pending state, its own saved confirmation and its own error presentation with a retry action.
- [ ] An edit buffer per section preserves the existing discipline: seeded once per distinct server answer by object identity, a dirty buffer is never reseeded by a late answer, and a save's own reply never discards keystrokes.
- [ ] Two independent buffers exist side by side without one section's server answer re-seeding the other's.
- [ ] The existing profile page is converted to the shell and the buffer, so a reader cannot find the old inline discipline any more.
- [ ] The existing profile page suite still passes unchanged apart from assertions that are provably about the old structure, and a new suite pins the buffer rules directly.

## Handoff notes

- **One blocker, and what it will have landed.** The ticket waits on the shadcn-primitives ticket, **#600**, because the shell renders a card. By the time this ticket starts, the frontend component-library directory will hold `Card`, `CardHeader`, `CardTitle`, `CardDescription`, `CardContent` and `CardFooter` alongside the already-adopted `Button`, `Avatar`, `DropdownMenu*`, `Sheet*` and `Skeleton`, and the frontend manifest will carry two new Radix runtime packages (the switch and the toggle group) that this ticket does not use directly. Import the card parts by name; do not hand-roll a card wrapper in the shell, and do not wait to re-check the token bridge - #600's brief fixes the exact token paths a new primitive may reference.
- **The two existing page-suite assertions are the contract. Do not rewrite them to fit the new structure.** They are the only thing in the tree that proves a late answer cannot discard keystrokes, and the parent explicitly chose them as the seam to preserve rather than replace. If the conversion renames a test id the two assertions reach for, that is a signal the conversion changed observable behaviour, not that the assertion should move. The acceptable edits to that suite are narrow and provable: test ids the new structure genuinely renames, and structural selectors. Everything else stays byte-for-byte.
- **Add a new suite that pins the buffer rules directly, and put it beside the buffer, not inside the page suite.** A hook or a small component that owns one buffer can be rendered in isolation and driven with `fireEvent`, which makes the three rules and the two-independence case testable without a page, a provider and a network mock. The existing page suite then proves the page still behaves; the new suite proves the rule. That split is also what lets a future section reuse the buffer without inheriting the page's fixtures.
- **Judgement call, recorded: the "one buffer per section" shape means the identity guard's input changes shape too.** Today `seededFrom` holds one `DoctorProfileView` and the buffer is one `ProfileForm`. With per-section buffers, each buffer's seed key is the _same_ server answer object - the whole projection from the shared source - while the value it produces is a per-section slice via a per-section mapper. Keep the guard reading the answer object identity, never the slice: two sections seeding from their own slices would reseed each other's fields the moment the source emitted a new object, which is exactly the drift the parent calls out when it says there are now four independent buffers instead of one.
- **Judgement call, recorded: a dirty flag is a boolean, not a per-field map, and it should stay that way.** The existing discipline is deliberately coarse: while the buffer is dirty, the doctor's intent outranks _every_ answer, including one that would fix a field they did not touch. Per-field dirt would be "better" and would be wrong here - it is a different design with a different rationale, and adopting it silently in a prefactor is how a later ticket ends up unable to reason about whether behaviour changed. If a sibling section ticket needs finer granularity, that is a deliberate change with its own tests.
- **Judgement call, recorded: `adoptRef` stays a page-level seam, it does not move into the buffer.** Its job is folding a single-field answer (a photo ref, its absence, a saved fee) into the mirrored projection and handing the whole view back through the source's one adopt seam. That is a concern about the _source_, not about any one section's buffer, and a buffer that could adopt would give a section the power to re-seed every other section. Keep the `newestProfile` mirror and `adoptRef` where they are.
- **The shell owns presentation and save lifecycle; it does not own validation or transport.** `invalidFields` and the whole-form request builder stay with the sections that use them, and the shell's retry action is a callback into whoever owns the attempt, not a fetch. This keeps the shell reusable by the notification section (whose save path is a different route) and by the credentials band (which is read-only and needs a shell with no save affordance at all). A shell that cannot render a section with no save button has over-specified itself.
- **Preserve the idempotency-key discipline while you are in there.** Both the save path and the photo-removal path keep a ref holding one key per _user attempt_: a retry of the same attempt reuses it so a lost response cannot write twice, and an edit mints a new one. That ref belongs with the attempt, so if the shell owns the save button, the shell owns the key ref too - or it takes a `pending`/`onSave` pair and the key stays with the section. Either is fine; silently dropping the reuse is not.
- **The shell is a new file under the frontend component directory, and it is "use client".** It renders interactive state (pending, dirty, saved) and Radix-backed card parts. The vitest config globs `src/**/*.test.{ts,tsx}` with colocated suites and no globals, so the new suite goes beside it and calls its own `afterEach(cleanup)`. There is no `user-event` in the repo - use `fireEvent`.
- **Relevant ADRs.** None directly. The two ADRs this parent work writes are reserved as **0021** (a profile save moves the public directory position) and **0022** (the practice position is a PIN centroid, not a geocode), both owned by **#622**; neither constrains a frontend shell, and neither blocks this ticket. The one ADR that shapes the surface indirectly is **ADR-0020** (profile media storage), whose D1 decision is why the photo is an opaque ref resolved through the shared resolver rather than a URL - if the shell ever takes a photo, it takes a resolved source, never a stored ref.
- **Not blocked, and worth knowing: this ticket is the shared source the section siblings all consume.** The practice, address, about and notification section-write tickets each need a shell and a buffer, and each also needs a new dictionary key in both locales for its own title and help text. Those keys are theirs, not this ticket's - the shell takes strings as props and adds no keys of its own except whatever generic save/saved/retry copy it presents, and those must ship in both locales or the parity suite fails.
- **Out of scope, do not drift into:** splitting the page into four section components (that is the siblings' job - this ticket only makes the shell and the buffer exist and makes the page use them), the four new section-write routes, the address/PIN work, the identity band, the anchor-chip index, the live preview, any new toggle group or switch adoption, and the axe scan.
