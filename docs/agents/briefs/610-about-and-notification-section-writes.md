# Brief - 610 Add the about and notification section writes

**Ticket:** #610 · **Parent:** #599 · **Refreshed:** 2026-09-30
**Reading surface:** ~8.4K tokens (budget 10K) - within budget
**Set position:** third of the three section-write briefs in this batch (#608, #609, #610). Read-list items 1-5, 6, 7, 8 and 10 are the same anchors as in #608 and #609, described the same way, so a reader moving between the siblings sees one set of seams. This is the only one of the three that lands **two** writes in one ticket.

## Scope

Languages become a validated selection from the scheduled-languages list, so a doctor cannot record the same language twice in two spellings. Availability splits - consulting days become a set the doctor taps, consulting hours stay prose they write themselves, so the half that benefits from structure has structure without implying a booking system the platform does not have. Notification preferences save on their own too.

### Acceptance criteria

- [ ] An about section write accepts about text, a multi-valued language selection validated against the closed list, multi-valued consulting days validated against the day list, and consulting hours as free prose.
- [ ] A notification section write accepts the five existing notification keys and touches only its own column.
- [ ] Both writes are scoped per doctor for idempotency keys and recheck that the doctor is active under a row lock.
- [ ] A value outside the language or day closed list is refused with a field-level detail in the standard validation envelope.
- [ ] Consulting hours stay prose - no weekly template, no slot structure, nothing that implies a booking system.

- **Judgement call - the five notification keys have no server-side name.** `notification_preferences` is an untyped `dict[str, bool]` with a 20-entry cap and a 50-character key cap, validated only for shape. The only named list of the five keys in the whole repository is the frontend `NOTIFICATION_KEYS` tuple (item 9), and #602 owns closed vocabularies for specialty, languages and consulting days - **not** for notification keys. So nothing you are waiting on gives the server a list to validate against. Two defensible answers: pin the five keys server-side in the notification request model, which makes "accepts the five existing notification keys" enforceable and refuses an arbitrary key, or keep the open dict and preserve the 20-entry cap. Pinning them is the stronger contract and matches the client comment's own claim that the page "owns the canonical key vocabulary", which is precisely the ownership that should move to the server. **Make the choice explicit in the closing comment**, because #617 builds the switches against it and #613 carries the same dict to the public profile.
- **Judgement call - the client's pass-through rule has a server consequence.** The client comment says a stored key the page does not know is carried through untouched on save, so a save never silently drops a preference. If you pin the five keys server-side, decide deliberately what happens to a stored key outside the five: refusing the whole write strands a doctor with a stale unknown key, and dropping it silently loses a preference. A merge that preserves unknown stored keys and validates only the known ones keeps the client's guarantee true on the server. Whatever you choose, assert it - this is the one place your two writes can disagree with the client about a save.
- **Judgement call - consulting hours are prose, and the model has to say so.** No weekly template, no slot structure, no per-day ranges, nothing that implies a booking system the platform does not have. The field is a bounded free string and the acceptance criterion is a round-trip of an arbitrary value. The easy mistake is introducing a shape that reads as bookable; if you find yourself modelling days-with-hours, stop - days are their own column from #606 and hours are one string.
- **Judgement call - languages keep the existing hygiene on top of the closed list.** `validate_languages` already strips whitespace and de-duplicates case-insensitively, which is the partial fix for the same-language-twice problem the ticket names. Your validator delegates to #602's membership entry point and **keeps** the strip and the case-insensitive de-duplication. Dropping them would let a member of the list arrive twice in two cases, which is the exact defect the ticket opens with.
- **Judgement call - how a closed-list rejection reaches the envelope.** A Pydantic field validator's `ValueError` does not automatically arrive as the `details.errors[{path, reason}]` shape the client renders against; the existing 422 precedent in the partner module is a registered handler on a typed domain error. Decide whether your closed-list refusal is a model-level rejection (which the framework encodes, path-keyed by field name, for free) or a typed domain error with a registered handler, and assert the resulting `path` names the language or day field. Getting this wrong produces a 422 the client cannot render under the offending input, which is the failure the ticket is trying to remove.
